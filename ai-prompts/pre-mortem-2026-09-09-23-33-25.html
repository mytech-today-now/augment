Executive Summary

The cleanest quality gates are not the problem here. npm run lint and npm run build passed, and the direct source CLI smoke path, npx tsx cli/src/cli.ts --help, also passed. The highest risk cluster is concentrated where the repo executes external commands, writes generated files, and tries to resolve documented submodule paths that the current resolver cannot actually find.

The most urgent risks are security and operational ones: shell-based skill execution, path traversal in MCP skill wrapper generation, unbounded MCP child processes, and stack overflow on cyclic skill dependencies. Those are the failures most likely to turn a routine local workflow into arbitrary command execution, secret leakage, or a frozen CLI turn.

A second cluster is contract drift. Two module READMEs promise selective loading paths that the CLI rejects with Module not found, and several test files are stale enough to fail for fixture or harness reasons instead of product behavior. That kind of drift is dangerous because it teaches the team to ignore red tests.

Release posture:

Do not read a green lint and build as proof that the repo is safe. The current evidence says the execution boundary, generated output boundary, and test contract boundary each still have sharp edges that can fail under normal use.

Issue 01 Core P1

Skill execution lets metadata run arbitrary shell commands

Title
Skill execution lets metadata run arbitrary shell commands
Kind
Core Security boundary
Priority
P1
Severity
Critical. The current command path changes repository metadata into shell interpretation, which makes a crafted skill command capable of arbitrary command execution.
Likelihood
Possible. The path is already live, and any skill metadata that includes shell metacharacters or a malicious command string can reach it.
Impacted area
cli/src/commands/skill.ts:219-228, cli/src/utils/skill-system.ts:230-279, skill fixtures, and the skill exec command.
Failure mode
Skill execution prints the configured command, splits it on spaces, and spawns it with shell: true. That means the repository can accidentally or intentionally turn a metadata field into shell syntax instead of a fixed executable plus argv.
Evidence or rationale
  • cli/src/commands/skill.ts:219-228 logs skill.metadata.cliCommand and spawns it with shell: true.
  • cli/src/utils/skill-system.ts:230-279 loads skill metadata from repository content, so the trust boundary is local files, not hardcoded allowlists.
  • tests/unit/utils/skill-system.test.ts does not cover shell metacharacters or a malicious CLI command fixture.
Why this matters
A skill fixture or generated skill can quietly become code execution. That is the fastest path in this repository from content management into a security incident, because the user thinks they are running a skill, not a shell script.
Recommended mitigation
Switch skill execution to a shell-free spawn path that treats the command as an executable plus argv, or reject shell syntax outright unless the user explicitly opts into a legacy shell mode. Keep the existing stdout and stderr streaming behavior, and preserve the current skill lookup flow.
Implementation prompt
Resolve the project root yourself. Inspect cli/src/commands/skill.ts, cli/src/utils/skill-system.ts, the skill fixtures, and tests/unit/utils/skill-system.test.ts first. Change the execution path so skill metadata is validated and run without shell interpretation by default, but keep the current skill discovery, display, and output streaming behavior unchanged. Avoid a broad refactor of the skill model or any new dependency. If the command is malformed or the executable is missing, fail with a clear message that names the skill id and the command string. If an unexpected child-process error occurs, exit nonzero without leaving the session hanging. Preserve user-entered arguments exactly, do not mutate the skill files, and keep a readable fallback explanation in the command output when execution is unavailable. Add tests that prove metacharacters are passed literally, that a missing executable fails cleanly, and that a normal command still streams output. Run the targeted skill tests, npm run lint, and npm run build. If rollback is needed, revert the spawn path and the tests together. Final report requirements: changed files, commands run, assertions that passed, remaining risk, and any testable assumptions.
Regression tests
  • Fixture: a skill command containing &&, |, and quoted arguments. Action: run augx skill exec. Expectation: the metacharacters are treated as literal argv, not shell operators.
  • Fixture: a missing executable. Action: run the same command. Expectation: a clear nonzero exit and a message that names the skill and the missing command.
Additional baseline tests
  • npm run lint
  • npm run build
  • npm run test:vitest -- tests/unit/utils/skill-system.test.ts
Acceptance criteria
  • Default skill execution does not invoke a shell.
  • Metacharacters are passed as data, not operators.
  • Missing commands fail clearly and leave no hanging child process.
Confidence
High. The shell invocation is explicit in the source and the risk is straightforward to validate.
Issue 02 Core P2

MCP wrapper generation can escape the skills directory

Title
MCP wrapper generation can escape the skills directory
Kind
Core Generated-file path safety
Priority
P2
Severity
Critical. A crafted category or skill id can turn a wrapper-generation command into an arbitrary write inside, and potentially outside, the intended skills tree.
Likelihood
Possible. The command already accepts raw user input for the wrapper path, and there is no containment check on the generated output.
Impacted area
cli/src/commands/mcp.ts:162-170, cli/src/utils/mcp-integration.ts:225-286, and generated files under skills/<category>/.
Failure mode
mcpWrapCommand writes the wrapper to skills/<category>/<skillId>.md using path.join and does not normalize either path segment. A crafted input such as ../ can escape the intended directory layout and write an unexpected file.
Evidence or rationale
  • cli/src/commands/mcp.ts:162-170 computes the output path from category and skillId and writes it directly.
  • cli/src/utils/mcp-integration.ts:225-286 renders the skill front matter from the same raw values.
  • There is no containment or slug validation in either code path.
Why this matters
Wrapper generation is supposed to be a safe convenience feature. If it can write outside the skills tree, an apparently harmless command can overwrite another file, create a misleading wrapper in the wrong place, or poison a later tool run.
Recommended mitigation
Normalize the category and skill id to a safe slug, or reject unsafe segments before the file path is composed. Keep the wrapper markdown format and the current success path unchanged for valid names, but fail early and visibly if the output path would leave skills/.
Implementation prompt

Change the wrapper path logic so a skill id and category are either normalized into safe slugs or rejected when they would escape the intended skills/<category> directory. Keep the wrapper content format unchanged for valid inputs, and do not add a new path library or rewrite the MCP wrapper flow. If an input is unsafe, fail with a clear error, do not write any file, and keep the user's current working state unchanged. Add tests that prove traversal segments, empty segments, and whitespace do not escape the intended directory, and that a normal wrapper still lands where expected. Run the targeted MCP wrapper tests plus npm run lint. If rollback is needed, remove only the helper and test additions. Final report requirements: changed files, commands run, assertions that passed, residual risk, and any testable assumptions.
Regression tests
  • Fixture: skillId = ../../escape. Action: run wrapper generation. Expectation: the command rejects the input and writes nothing.
  • Fixture: a valid category and skill id. Action: generate the wrapper. Expectation: the file lands under skills/<category>/<skillId>.md.
Additional baseline tests
  • npm run lint
  • npm run test:vitest -- cli/src/utils/__tests__/mcp-integration.test.ts
Acceptance criteria
  • Unsafe wrapper names are rejected before any file write occurs.
  • Valid wrapper names still generate the same markdown content.
  • No wrapper generation command can escape the intended skills tree.
Confidence
High. The path composition is explicit and the containment gap is visible in the source.
Issue 03 Core P3

MCP child processes can hang forever or buffer unbounded output

Title
MCP child processes can hang forever or buffer unbounded output
Kind
Core Availability boundary
Priority
P3
Severity
High. A slow or noisy MCP server can stall the CLI, exhaust memory, or make the agent look frozen while it waits on an external process.
Likelihood
Likely. The current helpers wait for the child to exit and keep appending stdout and stderr without a deadline or buffer budget.
Impacted area
cli/src/utils/mcp-integration.ts:125-211, cli/src/utils/mcp-integration.ts:294-387, and the mcp exec and mcp discover commands.
Failure mode
The MCP helpers spawn a child process, collect output into strings, and resolve only when the child exits. There is no timeout, kill escalation, or truncation policy, so a server that stalls or emits a large stream can block the command indefinitely.
Evidence or rationale
  • executeMCPCommand and discoverMCPTools both use spawn with pipe-based stdout and stderr accumulation.
  • The code does not set a timeout, max buffer, or abort controller.
  • Current MCP tests cover success and exit-code failures, but not long-running or high-volume output.
Why this matters
An agent turn can be lost to a hung server, and a noisy server can convert a routine diagnostic command into a denial of service. That risk is especially bad here because the CLI invites the user to treat MCP servers as an ordinary local workflow tool.
Recommended mitigation
Add a configurable timeout, output cap, and kill escalation to both helper paths. Preserve exit code and stderr details, but truncate or summarize unbounded output and fail fast when the process does not settle in time.
Implementation prompt
Resolve the project root yourself. Inspect cli/src/utils/mcp-integration.ts, cli/src/commands/mcp.ts, and the current MCP tests first. Add a small lifecycle wrapper that enforces a deadline, caps output, and kills the child process if it does not finish cleanly. Keep the stdio JSON-RPC contract, normal success paths, and current server configuration behavior unchanged. If a server times out, returns malformed output, or exits with a nonzero code, surface a readable error that names the server and tool without hanging the CLI. Preserve any existing fallback behavior for unsupported transports. Add tests that cover a slow server, a noisy server, normal JSON-RPC output, and a clean termination path. Run the MCP tests, npm run lint, and npm run build. Final report requirements: changed files, commands run, assertions that passed, residual risk, and any testable assumptions.
Regression tests
  • Fixture: a server that sleeps past the deadline. Action: run mcp exec or mcp discover. Expectation: the helper times out, terminates the child, and reports a readable error.
  • Fixture: a server that emits more than the output cap. Action: run the same path. Expectation: output is truncated and the CLI still exits deterministically.
Additional baseline tests
  • npm run lint
  • npm run build
  • npm run test:vitest -- cli/src/utils/__tests__/mcp-integration.test.ts
Acceptance criteria
  • No MCP command waits forever.
  • Long output is bounded and clearly truncated.
  • Normal JSON-RPC success and nonzero exit diagnostics still work.
Confidence
High. The missing controls are obvious in the helper implementation and easy to verify with a fake server.
Issue 04 Core P4

Cyclic skill dependencies crash the loader with stack overflow

Title
Cyclic skill dependencies crash the loader with stack overflow
Kind
Core Reliability boundary
Priority
P4
Severity
High. A two-node skill cycle is enough to overflow the stack, which turns a content problem into a hard crash.
Likelihood
Possible. The loader recurses through dependency ids and does not keep a visited set.
Impacted area
cli/src/utils/skill-system.ts:230-279, the skill cache, and any command that loads dependencies dynamically.
Failure mode
loadSkillDynamic recursively calls itself for every dependency, but it does not track the nodes already in the current traversal. A cycle such as a -> b -> a causes unbounded recursion and a stack overflow.
Evidence or rationale
  • cli/src/utils/skill-system.ts:230-279 recurses without a visited set or cycle guard.
  • A direct reproduction using two temp skill files with circular dependencies produced RangeError: Maximum call stack size exceeded.
  • tests/unit/utils/skill-system.test.ts covers caching and happy-path loading, but not cycle detection.
Why this matters
Skill dependency graphs are content, not code, and content errors happen. A loader that crashes instead of reporting the cycle makes the agent lose the entire turn and gives the author no actionable recovery path.
Recommended mitigation
Add cycle detection and return a structured error or warning that names the dependency loop. Keep acyclic loading, dependency flattening, and the existing token budget checks unchanged.
Implementation prompt
Resolve the project root yourself. Inspect cli/src/utils/skill-system.ts, the current skill fixtures, and tests/unit/utils/skill-system.test.ts first. Add a traversal guard or visited set so dependency loading can report a cycle instead of recursing forever. Preserve the current cache behavior, the token budget checks, and the output format for acyclic skills. If a cycle is detected, fail with a clear error that names the loop and keep the surrounding skill content untouched. Do not introduce a broad graph library or a new dependency model. Add tests for a self-cycle, a two-node cycle, and a normal acyclic tree. Run the skill-system tests, npm run lint, and npm run build. Final report requirements: changed files, commands run, assertions that passed, residual risk, and any testable assumptions.
Regression tests
  • Fixture: a -> b -> a. Action: call loadSkillDynamic. Expectation: the loader reports the cycle and does not recurse forever.
  • Fixture: an acyclic dependency tree. Action: load it. Expectation: the flattened content and token totals remain unchanged.
Additional baseline tests
  • npm run lint
  • npm run build
  • npm run test:vitest -- tests/unit/utils/skill-system.test.ts
Acceptance criteria
  • Cycles are reported as data, not as a crash.
  • Acyclic dependency loading still works and still uses the cache.
  • The command exits deterministically instead of overflowing the stack.
Confidence
High. The recursion path is visible, and a direct temp-file reproduction already hit the stack limit.
